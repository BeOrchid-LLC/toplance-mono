Toplance — who can access what

Three platform-wide roles, each mapped to its own console. Enforced in application code (src/lib/auth/policy.ts, guards.ts) — there is no database RLS.
BeOrchid / Toplance internal staff
Client organization employees
Traveller (end user)

Staff — BeOrchid / Toplance

Platform-wide · runs the product
reviewer owner
Console: /ops — gated by requireStaffConsole + Clerk 2FA (only role with this extra gate)
  • Read/write every traveller's application, documents, case notes
  • Review & verify documents, change case status, claim/release cases
  • Read the audit log
  • owner only: write corridor reference data (rare — normally seeded via script)
  • No self-serve signup — promoted via a manual SQL helper, on purpose

Org member — client organization

Scoped to their own organization only
hr_admin owner
Console: /employer — gated by requireOrgAccess. No access to /ops, ever.
  • Invite travellers to their org (invite-only sponsorship model)
  • View a read-only roster of sponsored travellers' progress (status only)
  • owner vs hr_admin is currently just a UI label — no permission actually differs between them today
  • Cannot see documents, case notes, messages, itinerary, or companion data for any traveller — see privacy boundary below

Traveller — end user

Scoped to themself only
traveler
Console: /app — the actual product
  • Read/write their own single application, documents, intake answers
  • Read-only on their own case notes and messages
  • Write their own itinerary and companion updates
  • Uniquely: the only role that can set their own visa expiry date — restricted even from staff
  • Invite-only since 2026-08-31: no self-serve traveller signup, must come via an org invitation

The privacy boundary — BeOrchid staff vs. the client's own employees

This is the core distinction the platform is built around: a client organization sponsors a traveller's visa case, but its employees (org_member) are treated as an outside party with a status dashboard, not as case handlers.

Functions like canReadDocuments, canReadCaseNotes, canReadMessages, canReadCompanion and canReadItinerary in policy.ts are commented "deliberately no sponsorship branch" — meaning sponsoring an application grants zero visibility into its private contents, by design, not by omission.

Only staff (BeOrchid/Toplance employees) and the traveler themself can see that data. Org admins only ever see aggregate/status-level progress for people they sponsored.
